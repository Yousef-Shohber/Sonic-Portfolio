Engineering decisions

01Session handling
Short-lived JWT access tokens and longer-lived refresh tokens are delivered as httpOnly cookies. Email OTPs for verification and password reset are held in Redis, and Google OAuth 2.0 is supported alongside email login.
02Role and resource-level authorization
Role-based guards separate tenant, owner, maintenance staff and admin capabilities. On top of roles, resource-level checks make sure owners and staff only act on the records that belong to them.
03Redis-backed rate limiting
Throttling is applied per IP and per user, with stricter limits on login, token refresh and OTP endpoints than on the general API.
04Cache-aside reads
Property, unit and listing reads are cached in Redis with a short, configurable TTL, and invalidated whenever the underlying records are created, updated or deleted.
05Upload validation
Files are checked by MIME type and magic bytes before they are sent to Cloudinary, instead of trusting the client-supplied content type.
06Predictable configuration and errors
Environment variables are validated with Zod at startup, schema changes are tracked with TypeORM migrations, and a global exception filter keeps stack traces out of production responses. Passwords are hashed with bcrypt.

Clinic Appointment System

Booking API with payments and real-time updates

A REST API for clinic appointment booking that prevents double-booking under concurrent requests using atomic Redis locks and Lua scripts. Background workers expire unpaid appointments, payments run through Paymob, and patients and doctors get live updates over Socket.IO.

  • Node.js
  • TypeScript
  • Express
  • MongoDB
  • Redis
  • BullMQ
  • Socket.IO
  • Paymob
  • Google OAuth
  • Cloudinary
  • Zod
  • Source on GitHubfor Clinic Appointment System (opens in a new tab)
Concurrency
The Redis lock handles contention at request time, and a unique compound index on doctor, date and start time exists as a database-level constraint.
Expiry
An expiration worker marks still-pending appointments as expired, refunds through Paymob if a payment was made, invalidates the cache and notifies the patient.
Webhook handling
The Paymob route uses a raw body parser mounted ahead of the JSON parser, and each callback is verified with an HMAC-SHA512 signature.
Tokens and limits
JWT refresh-token rotation with reuse detection, Redis-backed rate limiting and idempotency keys.

Event Booking & Queue Management

Capacity-safe booking with a FIFO waitlist

A booking API with real-time queue management. Slot capacity is decremented atomically in Redis, unconfirmed bookings expire through delayed BullMQ jobs, and a first-in-first-out waitlist promotes the next person automatically when a slot frees up.

  • Node.js
  • TypeScript
  • Express
  • MongoDB
  • Redis
  • BullMQ
  • Socket.IO
  • JWT
  • Google OAuth
  • Zod
  • Pino
  • Source on GitHubfor Event Booking & Queue Management (opens in a new tab)
Concurrency
Capacity is decremented atomically by a Redis Lua script before the MongoDB transaction records the booking, so concurrent requests cannot oversell a slot.
Expiry
Each booking gets a delayed BullMQ job. If it is not confirmed in time, the booking is marked EXPIRED, the Redis counter is released and the next person in the queue is promoted.
Waitlist
Waiting users sit in a Redis sorted set scored by join time. Promoted users get a confirmation deadline enforced by a delayed job, and are notified over WebSocket.
Tokens and limits
JWT refresh-token rotation with reuse detection, Redis-backed rate limiting on sensitive routes, and idempotency for booking and queue actions.

03About

Interested in the failure cases.

I enjoy the part of backend work that users never see: making sure two requests can’t book the same slot, a stolen refresh token can’t be replayed, and a failed payment doesn’t leave a half-finished record behind.

I’m a fourth-year Information Technology student at Zagazig University. I started with JavaScript and the MEAN stack, then narrowed in on the server side, where the interesting problems are correctness, security and what happens when things fail.

My early projects were Express APIs built around CRUD, authentication and role-based access. The later ones push into concurrency and background work: Redis Lua scripts for atomic reservations, BullMQ for expiry and notifications, Socket.IO for live updates. More recently I’ve moved to NestJS and PostgreSQL, and PropFlow is where I’m applying that structure end to end.
